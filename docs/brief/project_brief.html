CLINVEIL: an offline privacy firewall for messy, multilingual Indian hospital exports

Team APEX · Track 3 · Secret Wards (Yugaantar DevForge) · Repo: github.com/Amartya989870xxxx/CLINVEIL

1. In one paragraph

CLINVEIL takes a folder of real-world hospital exports and writes a sanitised release: every personal identifier is removed from every place it hides, clinical values stay exactly intact, and every real patient gets one stable keyed pseudonym across files, hospitals and scripts. The core idea: an identifier has an owner. A father's Aadhaar in a child's note, or a guardian's hospital in a referral, is evidence about a relative. It is used only to veto a link, never to make one. Linking is set-based and abstains when evidence conflicts, because a wrong merge harms patients more than a missed one.

3. How each part works

  • Ingestion: deterministic discovery; symlinks that escape the input are never opened; size, depth and node limits; content sniffing (signatures, JSON-first, delimiters); UTF-8/BOM/UTF-16 (incl. BOM-less)/cp1252 with mojibake and binary checks. Broken, unsupported or over-limit files are quarantined, never copied raw.
  • Parsing: one intermediate representation for CSV, TSV, JSON, FHIR R4 Bundles, plain text and declared or embedded base64 payloads. Every value carries its address, record and channel.
  • Detection, six channels: content, header, key, metadata, base64, filename. The layers are: column semantics (renamed and Hindi labels); validated Indian identifiers (Verhoeff Aadhaar, ABHA, PAN, MRN/UHID with dose guards); contextual Latin, Devanagari and Hinglish names and relatives; address components with gazetteers and transliteration; clinical and doctor protection (meaning traps); and run-wide propagation of confirmed values into notes, filenames, keys, headers, metadata and base64.
  • Linkage: typed evidence per record (global IDs, hospital-scoped MRNs, names via strict transliteration keys, DOB, phone, relatives, village), each with its owner. Confidence tiers: a validated global ID; a verified same-hospital MRN; a corroborated full name. Clusters form by complete linkage within each edge group. Ambiguous bridges and groups over 256 abstain and are frozen. Two different UHIDs from one issuer block a link unless the documented re-registration evidence is present.
  • Pseudonyms: domain-separated, versioned HMAC-SHA256 of a patient key. With a different secret the outputs cannot be linked. No plaintext mapping is ever persisted.
  • Sanitisation: typed placeholders ([NAME], [MRN]…); PII numbers become 0 (type kept); FHIR birthDate keeps the year only; payloads are re-encoded; binary attachments are withheld; FHIR references are rewritten consistently; PII-bearing paths are renamed.

4. USP

  • Ownership-aware identity: relative-owned IDs, ages, genders and facilities can veto a link but never create one. This also holds inside XHTML narratives (tables, definition lists, paragraphs).
  • Cross-script, conservative linking: one patient as Latin, Devanagari and Hinglish is linked through strict transliteration keys plus corroboration. Homonyms, household phones and shared visit numbers do not merge people.
  • No raw copies, no side channels: secret only in memory, PII-free reason codes in logs, no temp files written, and an in-process contract check before exit 0.

5. Security design

Assume a breach: the release contains no direct identifiers and no mapping table. The key lives only in the RAKSHA_SECRET environment variable (an unprintable object, never logged). Logs carry reason codes, not values. The process writes no temporary files, so there is nothing to clean up or leak from TMPDIR; there is therefore also no encryption at rest. Input files are never modified (verified by hash before and after). Engine dependencies: none beyond the Python standard library; no network, no LLM.

6. Privacy layer: what the submitted code applies

TransformationStatus (implemented, integrated, tested)
Direct identifiers (names, relatives, Aadhaar, ABHA, PAN, MRN, phone, e-mail, insurance)Applied: typed placeholders in all six channels
Per-patient date shift (secret offset, |shift| ≤ 180 days, never 0)Applied to structured date fields (CSV, TSV, JSON, nested JSON, FHIR period/effectiveDateTime/authoredOn…), date-named keys and full dates inside free text (notes, narratives), keeping notation, time and zone. Linked patient: one HMAC offset across all files, so intervals and length of stay are exact. Unlinked record: its own keyed offset, never shared. Day/month order is inferred per document (one source is month-first); ambiguous dates with no order evidence are suppressed as [DATE], never guessed or kept (33 on practice). Export/audit timestamps (lastUpdated, generated_at) are not shifted.
Age (policy age_band_years: 5)Applied to structured ages and age/sex values: 47 → 45-49, 73/F → 70-74/F (the band always contains the age). Not banded: JSON numeric ages (to keep the value type; a numeric band bound would be untruthful), ages inside free text, and non-year ages (“6 months”).
DOBApplied: removed in text and fields ([DOB]); FHIR birthDate keeps the year only. Consistent with banded ages.
PIN (planned 3-digit prefix)Applied: 226010 → 226XXX in structured and text fields, only where the rare-cell rule allows. Otherwise [PIN]. Filenames and base64 always [PIN].
Rare-cell protection (policy min_group_size: 5)Applied to the PIN prefix: a record keeps its prefix only if at least 5 records of the same document share (age band, gender, PIN prefix). Missing values count as their own value, so small files are fully suppressed. On practice data only 5 of 136 PINs keep a prefix. This is not formal k-anonymity: other quasi-identifiers are not suppressed, and the scope is one document.
Village → tehsil/districtNot implemented: no offline mapping exists in the repo (none invented). Villages, houses, localities and landmarks stay fully suppressed; tehsil/district/state fields are kept.

Trade-off. Clinical values are untouched and date intervals are exact. We give up exact visit dates, exact ages and full PINs (the utility scorer credits a 5-year band at 0.9 and a true PIN prefix at 0.7) to resist visit-date and register-linkage attacks. Where no truthful generalisation exists (village), we suppress rather than invent.

8. Assurance

The identity-resolution layer (Phase 3) went through repeated independent security audits. Each finding was reproduced, fixed and given permanent tests. The latest targeted audit (Phase 3.3 Pass 4: XHTML relative ownership, and distinct-UHID enforcement against shared visit numbers) was approved. That approval covers those findings only, not the whole system.

9. Known limitations (honest)

  • Privacy layer partial: ambiguous day/month dates without order evidence are suppressed (utility cost); audit timestamps stay unshifted; JSON numeric and free-text ages are not banded; no village→tehsil/district generalisation; rare-cell protection covers the PIN prefix only, per document; not formal k-anonymity. Phase 4 has not been independently audited.
  • OBS-1, multi-block relative ownership: in a narrative laid out as "Father" → name in one block → age and Aadhaar in a later block, the relative's values can fall outside the ownership context window and be attributed to the patient. This is unresolved and can cause a false merge in affected layouts.
  • OBS-2: a Devanagari danda (।) next to a gender word can reduce gender recall in free text.
  • Free-text demographics with an ambiguous owner are dropped (precision over recall). The relative-name veto ignores relation type, so some same-patient records stay split.
  • Kinship and facility detection is word-list based. Hex encodings inside plain text are not decoded.
